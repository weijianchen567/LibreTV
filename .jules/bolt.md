## 2024-07-28 - Caching IO-bound operations vs CPU-bound operations in Node.js
**Learning:** Initially, when attempting to cache the `renderPage` HTML response, including an asynchronous `fs.promises.stat` on every request to invalidate the cache was actually slower (~1800 req/sec) than synchronously reading the file using `fs.readFileSync` (~2200 req/sec) because the OS already caches the small static files efficiently and the overhead of the asynchronous event loop scheduling for `fs.stat` on every single request became the new bottleneck. Furthermore, `renderPage` contained CPU-bound `SHA256` hashing which needed to be avoided.
**Action:** When caching read-heavy endpoints in Node.js, avoid triggering an asynchronous `fs.stat` on every request. Instead, rely on file watchers (`fs.watch`) or memory-only caches for static content without checking `mtime` on every tick, and ensure CPU-bound operations like crypto hashing are pre-calculated at startup when they don't depend on request-specific data.
